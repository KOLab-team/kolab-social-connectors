# KOLab Meta app migration plan

## 1. Objective

Create a new KOLab-owned production Meta app set that supports both social
publishing and customer messaging, pass Meta App Review, and migrate the
central KOLab Social Connectors service from the existing Postiz Meta apps
without losing client integrations, inbox history, or messages.

The target is one centrally hosted, multi-tenant KOLab service. KOLab owns the
Meta apps and server-side app secrets. Each client authorizes their own social
accounts through OAuth, and their tokens, integrations, posts, conversations,
and messages remain scoped to their KOLab organization.

## 2. Guiding decisions

1. Keep the existing Postiz Meta apps and credentials unchanged while the new
   KOLab apps are built, tested, and reviewed.
2. Use the new KOLab apps for both publishing and messaging so clients only
   need one connection per social account after migration.
3. Use Facebook Login for Business as the primary Facebook and Instagram
   Business connection path.
4. Treat Instagram Login as an optional separate connection path. Do not
   include it in the first review unless KOLab has clients who cannot link an
   Instagram professional account to a Facebook Page.
5. Treat Threads as publishing and public-reply management. Threads direct
   messages are not available through the public API used by this service.
6. Add temporary dual-app support before production cutover so old tokens and
   webhooks continue to work while clients reconnect through the new app.
7. Do not delete or recreate existing `Integration` records during migration.
   Reconnection must replace credentials on the existing integration so posts,
   inbox conversations, notes, and history retain their relationships.

## 3. Meta app topology

Meta exposes separate credentials for some product families, so the production
setup should be considered an app set rather than assuming one identifier will
cover every platform.

| App/configuration                 | Capabilities                                                                                                            | Service variables                          |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| KOLab Facebook/Instagram Business | Facebook Page publishing, Messenger, Instagram publishing, comments, insights, and Instagram DMs through Facebook Login | `FACEBOOK_APP_ID`, `FACEBOOK_APP_SECRET`   |
| KOLab Threads                     | Threads publishing, insights, reading public replies, and publishing public replies                                     | `THREADS_APP_ID`, `THREADS_APP_SECRET`     |
| KOLab Instagram Login (optional)  | Direct Instagram professional-account login, publishing, and DMs without Facebook Page discovery                        | `INSTAGRAM_APP_ID`, `INSTAGRAM_APP_SECRET` |

All production apps/configurations must be owned by the KOLab Business
Portfolio rather than an employee's personal business account. Assign at least
two KOLab administrators and require multi-factor authentication.

## 4. Global versus tenant-owned data

### Global server configuration

The following values identify KOLab's reviewed Meta applications and are
configured once per service environment:

```env
FACEBOOK_APP_ID="<new-kolab-facebook-app-id>"
FACEBOOK_APP_SECRET="<new-kolab-facebook-app-secret>"

THREADS_APP_ID="<new-kolab-threads-app-id>"
THREADS_APP_SECRET="<new-kolab-threads-app-secret>"

# Optional; only when the standalone Instagram connection is launched.
INSTAGRAM_APP_ID="<new-kolab-instagram-app-id>"
INSTAGRAM_APP_SECRET="<new-kolab-instagram-app-secret>"

# Generated by KOLab. Enter this same value in the Meta webhook dashboard.
META_WEBHOOK_VERIFY_TOKEN="<long-random-secret>"
META_GRAPH_VERSION="v25.0"
```

App secrets and webhook verification tokens must remain server-side and must
never be returned to a browser, placed in a `NEXT_PUBLIC_` variable, committed
to Git, or given to clients.

### Per-client data

Every authorized social account produces client-specific data:

- OAuth access and refresh tokens;
- Facebook Page, Instagram professional-account, or Threads account IDs;
- granted permissions and token-expiration state;
- posts and publishing history;
- inbox contacts, conversations, messages, attachments, and internal notes.

The existing inbox schema and authenticated endpoints use `organizationId` and
`integrationId` boundaries. Before launch, add tests proving that a user from
one organization cannot list, read, reply to, update, retry, or sync another
organization's conversations.

## 5. Production URLs

Choose stable production hostnames before configuring the Meta apps. Meta App
Review evidence and OAuth configuration should use the final URLs.

### OAuth redirect URLs

```text
https://<frontend-host>/integrations/social/facebook
https://<frontend-host>/integrations/social/instagram
https://<frontend-host>/integrations/social/threads
```

Only if standalone Instagram is launched:

```text
https://<frontend-host>/integrations/social/instagram-standalone
```

The configured URLs must exactly match the redirects produced from
`FRONTEND_URL`, including scheme, hostname, path, and trailing-slash behavior.

### Webhook callback URLs

```text
https://<backend-host>/social-inbox/webhooks/facebook
https://<backend-host>/social-inbox/webhooks/instagram
```

The callback URLs must be publicly reachable over HTTPS with a valid
certificate. They must not require KOLab session authentication. Payloads are
instead authenticated using Meta's `X-Hub-Signature-256` signature and the
appropriate app secret.

## 6. Meta app creation and base configuration

Meta changes dashboard labels periodically, but the required configuration is:

1. Open Meta for Developers and create the new production app under the KOLab
   Business Portfolio.
2. Select the business-oriented use cases/products that expose Facebook Login
   for Business, Facebook Pages APIs, Messenger, and Instagram Graph API.
3. Create or configure the Threads use case and record its Threads App ID and
   Threads App Secret.
4. Add the optional Instagram Login configuration only if it is part of the
   initial launch.
5. Under the app's basic settings, provide:
   - KOLab app display name and icon;
   - production app domain;
   - privacy-policy URL;
   - terms-of-service URL;
   - user-data deletion instructions or callback;
   - a monitored support/contact email;
   - the KOLab Business Portfolio and required verification details.
6. Add the exact OAuth redirect URLs from section 5.
7. Add KOLab developers, testers, and test assets while the app remains in
   Development mode.
8. Do not switch the app to Live mode until the required permissions have
   Advanced Access and the production service has passed the launch checklist.

## 7. Permissions requested by the service

Only request permissions that the product genuinely uses and that can be shown
clearly during review.

### Facebook Page publishing and Messenger

```text
pages_show_list
business_management
pages_manage_posts
pages_manage_engagement
pages_read_engagement
pages_manage_metadata
pages_messaging
read_insights
```

Key messaging permissions:

- `pages_messaging` allows the app to respond as an authorized Page, subject to
  Meta's messaging policies and window.
- `pages_manage_metadata` is used to subscribe the selected Page to KOLab's
  webhook application.

### Instagram Business through Facebook Login

```text
instagram_basic
instagram_content_publish
instagram_manage_comments
instagram_manage_messages
instagram_manage_insights
pages_show_list
pages_read_engagement
pages_manage_metadata
business_management
```

The client must authorize a Facebook Page connected to an Instagram
professional account.

### Instagram Login, if launched

The current standalone provider requests its Instagram publishing permissions
plus:

```text
instagram_business_manage_messages
```

Review the standalone provider's complete scope list immediately before the
review submission and make the dashboard request match the code exactly.

### Threads

```text
threads_basic
threads_content_publish
threads_read_replies
threads_manage_replies
threads_manage_insights
```

Threads messages represented in the KOLab inbox are public replies to posts,
not direct messages.

## 8. Webhook configuration

### Facebook Page webhook fields

Subscribe to the fields the application processes:

```text
messages
message_echoes
message_deliveries
message_reads
messaging_postbacks
messaging_optins
```

`message_echoes` is important for matching messages sent by KOLab or another
Page inbox back to the pending outbound record and avoiding duplicate message
rows.

### Instagram webhook fields

```text
messages
messaging_seen
```

### Webhook behavior requirements

The production handler must:

1. answer Meta's verification challenge using `META_WEBHOOK_VERIFY_TOKEN`;
2. verify `X-Hub-Signature-256` against an active app secret;
3. enqueue the payload and return HTTP 200 quickly;
4. normalize and process the event asynchronously;
5. deduplicate repeated deliveries;
6. route the receiving Page/account ID to the correct integration and
   organization;
7. retain sufficient structured logs to diagnose failures without logging
   access tokens or full sensitive message payloads.

After OAuth account selection, the service must subscribe the selected Page or
Instagram account to the new app. Dashboard-level webhook configuration alone
does not subscribe every client Page.

## 9. Pre-review engineering work

Complete the following before recording the review submission.

### 9.1 Dual-app credential support

The current service reads one App ID and App Secret per provider. Add a
temporary credential registry supporting `legacy` and `primary` credential
sets.

Recommended temporary variables:

```env
# New app used for all new OAuth authorizations.
FACEBOOK_APP_ID="<new-app-id>"
FACEBOOK_APP_SECRET="<new-app-secret>"
THREADS_APP_ID="<new-threads-app-id>"
THREADS_APP_SECRET="<new-threads-app-secret>"

# Existing Postiz apps retained only during migration.
FACEBOOK_LEGACY_APP_ID="<old-app-id>"
FACEBOOK_LEGACY_APP_SECRET="<old-app-secret>"
THREADS_LEGACY_APP_ID="<old-threads-app-id>"
THREADS_LEGACY_APP_SECRET="<old-threads-app-secret>"
```

If standalone Instagram is migrated, add equivalent legacy Instagram
variables.

Implementation requirements:

- All newly generated OAuth URLs use the primary app.
- Add an app/credential-set marker to each integration, or otherwise preserve
  which app issued its refreshable token.
- Backfill current production integrations as `legacy` before switching the
  OAuth default.
- Reconnecting through the new app changes the existing integration to
  `primary` without changing its integration ID.
- Webhook signature validation accepts every explicitly configured active app
  secret during the migration window.
- Token refresh selects the secret belonging to the app that issued the token,
  particularly for Threads and standalone Instagram.
- Logs identify the credential-set name but never the App Secret or token.
- Remove legacy support after the migration is verified and the rollback
  window has expired.

### 9.2 Graph API version consistency

The inbox uses `META_GRAPH_VERSION`, while some existing OAuth and provider
requests contain hard-coded Graph API versions. Move supported Meta requests to
a reviewed, centrally configured version where the product permits it. Test all
OAuth, publishing, sync, and messaging flows against that version before App
Review.

### 9.3 Tenant-isolation tests

Add automated tests covering:

- conversation list and search;
- conversation detail;
- status changes;
- outbound messages and retries;
- internal notes;
- manual sync;
- webhook routing when multiple organizations are connected;
- the behavior when the same external social account is presented for a
  second organization.

Decide whether one external Page/account may be connected to multiple KOLab
organizations. The recommended production rule is one active owner
organization per provider account, enforced during connection, unless explicit
agency sharing is implemented.

### 9.4 Token security

Before multi-client production launch:

- encrypt OAuth tokens at rest with a server-managed encryption key or secrets
  service;
- redact tokens, authorization codes, App Secrets, and signature inputs from
  logs and error reporting;
- restrict database and production environment access;
- define rotation and incident-response procedures;
- alert on expired/revoked tokens and surface a reconnect action;
- confirm database backups are encrypted and restoration is tested.

### 9.5 Product and policy surfaces

Provide production-accessible pages or endpoints for:

- privacy policy;
- terms of service;
- user-data deletion instructions/callback;
- disconnecting an integration and revoking its usable credentials;
- deletion or retention of messages and attachments;
- support contact information.

Document what KOLab stores, why it stores it, how long it is retained, who can
access it, and how a client requests deletion.

## 10. Development-mode end-to-end testing

Use KOLab-controlled test assets while the app is in Development mode:

- a Facebook Page;
- a Facebook user with the necessary Page task/access;
- an Instagram professional account linked to the Page;
- a separate Facebook/Instagram consumer account that initiates messages;
- a Threads account and a separate account that posts public replies.

Test at least these flows:

| Area                 | Test                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------- |
| OAuth                | Connect, cancel, deny one permission, reconnect, and revoke access                       |
| Facebook publishing  | Text, image/video where supported, scheduled post, and API error                         |
| Instagram publishing | Image, video/reel where supported, carousel, and invalid media                           |
| Threads publishing   | Text/media post, refresh token, and API error                                            |
| Facebook inbox       | Receive a user-initiated message, attachment, echo, delivery, and read event             |
| Instagram inbox      | Receive a user-initiated DM, attachment, outbound reply, and seen event                  |
| Threads inbox        | Import public replies and publish a reply to the correct root/reply                      |
| Reliability          | Duplicate webhook, delayed webhook, worker retry, manual sync, and missed-webhook repair |
| Tenancy              | Two organizations with different social accounts and attempted cross-org access          |
| Lifecycle            | Token expiration/revocation, reconnect, disconnect, and data deletion                    |

Facebook and Instagram test conversations must be initiated by the consumer
account. Test responses inside and outside the normal messaging window and make
sure the UI reports policy/API failures accurately.

## 11. App Review package

Prepare a concise review packet for every requested permission.

### Required material

- verified KOLab business details;
- stable reviewer login or a documented test path;
- privacy policy, terms, and data-deletion information;
- exact step-by-step reviewer instructions;
- test Page/Instagram/Threads assets where Meta permits them;
- screencasts showing the permission in actual use;
- a written explanation of why the permission is necessary and what happens if
  it is not granted.

### Recommended screencast sequence

1. Sign in to KOLab as a client organization user.
2. Open social integrations and choose Facebook/Instagram.
3. Complete Meta OAuth and select a Page connected to an Instagram
   professional account.
4. Show the connected integration in KOLab.
5. Create and publish a Facebook post.
6. Create and publish an Instagram post.
7. From a separate consumer account, send the Page a Messenger message.
8. Show the message arriving in the KOLab inbox.
9. Reply from KOLab and show the response in Messenger.
10. Repeat the receive-and-reply demonstration for Instagram DMs.
11. Show disconnect and user-data deletion behavior.
12. Record a separate focused Threads flow showing publishing, importing a
    public reply, and responding publicly.

Avoid submitting permissions that are not visible in the recording. Keep each
review explanation tied to a clear user action and business purpose.

## 12. Deployment strategy

### Phase A: Prepare infrastructure

1. Select the production frontend and backend hostnames.
2. Deploy the connector behind public HTTPS.
3. Configure PostgreSQL, Redis, workers, cron, backups, and monitoring.
4. Apply the Prisma schema using the repository's approved deployment process.
5. Confirm webhook endpoints are reachable and preserve the raw request body
   required for signature validation.

### Phase B: Run the new app in Development mode

1. Configure the new credentials in a staging environment.
2. Add only KOLab app-role users and test assets.
3. Complete the full test matrix.
4. Fix all permission, webhook, token-refresh, and tenant-isolation failures.

### Phase C: Submit and pass App Review

1. Complete Business Verification if required.
2. Submit permissions with the review package.
3. Answer reviewer questions and resubmit narrowly when necessary.
4. Confirm Advanced Access for every permission used in production.
5. Confirm the new app can be placed in Live mode for users who are not app
   roles.

### Phase D: Enable dual-app production mode

1. Deploy dual-app code without changing the existing primary OAuth app.
2. Backfill every existing integration as `legacy`.
3. Configure the legacy credentials from the existing production deployment.
4. Configure the reviewed KOLab credentials as `primary`.
5. Verify old webhook signatures, old publishing tokens, and refresh paths
   still work.
6. Change new OAuth and reconnect flows to use the primary KOLab app.

### Phase E: Client migration

Migrate a small internal/canary organization first, followed by client cohorts.

For each connected account:

1. notify the client of the reconnect requirement;
2. have an authorized Page/account administrator open the existing integration
   and choose **Reconnect**;
3. authorize the new KOLab app and grant the requested permissions;
4. ensure the selected external account ID matches the existing integration;
5. update the existing integration token and credential-set marker;
6. subscribe the Page/account to the new app's webhooks;
7. test one publish operation;
8. initiate a test message and verify it reaches the correct KOLab inbox;
9. reply from KOLab and verify delivery;
10. mark the integration migrated with timestamp and operator identity.

Track migration status per integration, not just per client, because one client
may connect several Pages and accounts.

### Phase F: Retire the legacy apps

Do not retire legacy credentials until:

- every active integration is marked `primary`;
- no webhook has validated only with a legacy secret during the agreed
  observation window;
- no token refresh is using legacy credentials;
- publishing and inbox health metrics are normal;
- support confirms there are no unresolved reconnect cases;
- a database backup and rollback snapshot exist.

Then remove the old Page subscriptions where appropriate, revoke unused legacy
tokens, remove legacy environment variables, delete the temporary dual-app
code, deploy, and only afterward retire the old Postiz Meta app configuration.

## 13. Rollback plan

During migration, the old Meta apps must remain Live and their credentials must
remain available to the service.

If the new app causes widespread OAuth, publishing, or messaging failures:

1. stop new migration cohorts;
2. switch new OAuth initiation back to the legacy app;
3. leave already migrated integrations on the primary app if healthy;
4. continue accepting signatures and refresh operations for both credential
   sets;
5. restore the previous deployment if the application change is the cause;
6. do not overwrite migrated tokens with database-wide scripts;
7. diagnose by integration and credential-set marker;
8. resume only after the canary test matrix passes again.

If a client reconnects to the new app but it is unusable, reconnect that same
existing integration through the legacy app. Never delete and recreate the
integration as a rollback shortcut.

## 14. Monitoring and operational readiness

Add dashboards and alerts for:

- OAuth callback success/failure by provider and credential set;
- integrations requiring reconnection;
- webhook verification and signature failures;
- webhook processing latency and queue depth;
- duplicate webhook rate;
- inbox sync failures;
- outbound message failure/retry rate;
- publishing failure rate;
- Meta rate-limit and policy-window errors;
- token refresh failures and upcoming expirations;
- unexpected webhook account IDs with no matching integration.

Define an operator runbook for token revocation, webhook outages, Meta API
version changes, app-secret rotation, compromised credentials, client deletion,
and queue/database recovery.

## 15. Client communication

Send clients advance notice explaining:

- KOLab is moving to a dedicated reviewed Meta application;
- existing scheduled content and inbox history will remain in KOLab;
- an authorized Page/account administrator must reconnect each integration;
- the reconnect screen will show both publishing and messaging permissions;
- Facebook and Instagram messages must be initiated by the consumer and remain
  subject to Meta policy windows;
- Threads inbox functionality covers public replies rather than direct
  messages;
- the deadline and support channel for completing migration.

Provide screenshots or a short video of the reconnect path and send reminders
only to organizations with unmigrated active integrations.

## 16. Definition of done

The migration is complete when:

- [ ] KOLab owns and administers the production Meta app set.
- [ ] Business Verification and all required reviews are complete.
- [ ] Required permissions have Advanced Access and the apps are Live.
- [ ] Production OAuth redirects and webhook callbacks use final HTTPS URLs.
- [ ] Webhook signatures, queues, deduplication, and account routing are tested.
- [ ] Tokens are encrypted at rest and redacted from logs.
- [ ] Tenant-isolation tests pass.
- [ ] Facebook and Instagram publishing works for non-role client users.
- [ ] Facebook Messenger and Instagram DM receive/reply flows work for
      non-role client users.
- [ ] Threads publishing and public reply flows work for non-role client users.
- [ ] Every active integration has reconnected through the new app.
- [ ] Existing integration IDs and historical data were preserved.
- [ ] No production traffic depends on legacy app credentials.
- [ ] Legacy variables and temporary dual-app support have been removed.
- [ ] The old Postiz Meta apps have been retired only after the rollback window.
- [ ] Monitoring, backups, deletion procedures, and the operator runbook are in
      place.
